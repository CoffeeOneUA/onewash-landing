# One Wash — Landing Page + запис онлайн

Промо-сайт автомийки **One Wash** (Тернопіль, вул. Протасевича 11А) з калькулятором запису, реальним прайсом і онлайн-оплатою через WayForPay.

## Структура

- `index.html` — готовий до деплою статичний файл головної сторінки (шрифти, лого, фото вбудовані як `data:` URI).
- `success.html` / `payment-failed.html` — окремі готові до деплою сторінки результату оплати (успіх / неуспіх), теж повністю самодостатні (шрифти й лого вбудовані).
- `template.html`, `success-template.html`, `failed-template.html` / `build.js` — вихідники для перезбірки всіх трьох сторінок (плейсхолдери `__..._B64__`). Одна команда `node build.js` перезбирає всі три.
- `api/` — серверні функції Vercel (Node, без зовнішніх залежностей — лише `fetch` до Supabase REST і WayForPay):
  - `prices.js` — GET, живі ціни (`wash_prices`), назви/тривалість типів мийки та авто (`wash_types`, `vehicle_types`) і активні додаткові послуги (`extra_services`). Прайс-таблиця й калькулятор на сайті тепер завантажують дані звідси при кожному відкритті сторінки, а не показують зашитий у білд знімок — інакше зміна ціни в адмінці не відображалась би на сайті, поки хтось вручну не перезбере й не задеплоїть його заново.
  - `available-slots.js` — GET, повертає вільний час на дату з урахуванням `location_working_hours`, `staff_schedule`, `staff_schedule_dates`, зайнятості майстрів і зайнятості боксів (`wash_boxes`, з урахуванням `is_active`) з `bookings`, а також "м'яких" утримань слоту від недавніх `payment_links` зі статусом `pending` (див. розділ нижче).
  - `create-payment.js` — POST, рахує ціну **на сервері** (не довіряє даним з браузера), перевіряє слот ще раз, створює запис у `payment_links`, повертає підписаний запит на оплату WayForPay. `returnUrl` веде на `api/return.js`, а не напряму на статичну сторінку.
  - `return.js` — GET/POST, приймає повернення браузера з WayForPay (це POST, а не GET!) і 302-редіректить на `/success.html?order=...`, щоб статична сторінка завжди коректно віддавалась. `success.html` сам собі перенаправляється на `/payment-failed.html?order=...`, якщо реальний статус виявиться "не оплачено".
  - `wayforpay-callback.js` — webhook (`serviceUrl`), перевіряє підпис WayForPay, після підтвердженої оплати викликає `_lib/completeBooking.js`, оновлює `payment_links`.
  - `order-status.js` — GET, статус платежу за `order_reference` для сторінок `success.html`/`payment-failed.html`. Якщо статус ще `pending`, **активно** запитує реальний статус у WayForPay (`CHECK_STATUS`) замість пасивного очікування вебхука — і сам завершує бронювання, якщо оплата насправді пройшла.
  - `_lib/completeBooking.js` — спільна ідемпотентна логіка "оплата підтверджена → створити клієнта/авто/`bookings`/`booking_extras`". Викликається і з вебхука, і з активної перевірки в `order-status.js`; безпечно викликати двічі для того самого запису. Поля, які пишуться в `bookings` (`payment_status: 'paid'/'partial'`, `prepayment_status: 'paid'`, без вигаданого `prepayment_amount`), навмисно повторюють `mage-wash-client/supabase/functions/wayforpay-webhook` — це те, що реально читає адмін-панель (`onewash-worker-app`).

## Змінні середовища (Vercel → Settings → Environment Variables)

| Змінна | Призначення |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | Обхід RLS для запису підтверджених записів (тільки на сервері) |
| `WAYFORPAY_MERCHANT_ACCOUNT` | Логін мерчанта WayForPay |
| `WAYFORPAY_SECRET_KEY` | Секретний ключ підпису WayForPay |
| `WAYFORPAY_DOMAIN` | Домен, прив'язаний до мерчант-акаунту (напр. `onewash-landing.vercel.app`) |
| `SUPABASE_URL` | (опційно) інакше береться дефолтний URL проєкту One Wash |

## Захист від "оплата пройшла, а запису немає"

Після реального інциденту (клієнт оплатив, гроші списались, а бронювання не з'явилось і бокс лишився вільним для подвійного запису) додано кілька незалежних рівнів захисту, які не покладаються лише на вебхук WayForPay:

1. **Активна перевірка статусу** (`order-status.js`) — поки клієнт на сторінці підтвердження, сайт не просто чекає вебхук: якщо `payment_links` ще `pending`, сервер сам питає WayForPay (`CHECK_STATUS`), і якщо оплата насправді пройшла — сам довершує бронювання. Спрацює, навіть якщо вебхук взагалі не дійде.
2. **Ідемпотентне завершення** (`_lib/completeBooking.js`) — і вебхук, і активна перевірка викликають одну й ту саму функцію; повторний виклик для вже обробленого платежу нічого не робить, тож гонка між ними безпечна.
3. **М'яке утримання слоту під час оплати** (`_lib/availability.js`, `PENDING_HOLD_MINUTES = 20`) — поки `payment_links` в статусі `pending` і не старіший за 20 хв, його майстер/бокс/час враховуються як зайняті і в `available-slots`, і при повторній перевірці в `create-payment`. Це закриває саме той сценарій з інциденту: адмін більше не зможе вручну записати іншу людину на слот, поки клієнт саме оплачує на сайті.
4. **`api/return.js`** — WayForPay повертає браузер клієнта на `returnUrl` через **POST**, а не GET. Прямий POST на статичний `index.html` на Vercel міг віддавати порожню/помилкову сторінку ("білий екран") ще до того, як встигав завантажитись JS. Тепер `returnUrl` веде на serverless-функцію, яка приймає будь-який метод і робить 302-редірект на окрему сторінку результату — вже гарантованим GET-запитом.
5. **Окремі сторінки результату оплати** (`success.html`, `payment-failed.html`) замість повернення на головну. `success.html` показує явний стан (перевіряємо / успіх / ще обробляється), деталі запису (дата, час, скільки оплачено і скільки лишилось внести на місці), посилання "Додати в календар" (.ics-файл) і "На головну"; якщо статус виявляється `failed`, сам перенаправляє на `payment-failed.html`. `payment-failed.html` пояснює, що гроші не списані й час лишився вільним, і пропонує спробувати ще раз або зателефонувати — а також підстраховується: якщо платіж насправді пройшов (гонка з ретраєм), сам перенаправляє назад на `success.html`.

## Відомі припущення, які варто перевірити перед реальними платежами

1. **`weekday` в `location_working_hours` / `staff_schedule`** — код вважає, що це ISO-конвенція (1=понеділок…7=неділя). Якщо у вас 0=неділя…6=субота, поміняйте `WEEKDAY_ISO` у `api/_lib/availability.js`.
2. **`bookings.status`** — код пише `'confirmed'`. У БД це звичайний `text` без обмежень, але переконайтесь, що адмінка коректно відображає саме цей рядок статусу (не якийсь інший, напр. `'scheduled'`).
3. **Інтеграція WayForPay не тестувалась на реальному акаунті через `CHECK_STATUS`** — обов'язково проведіть тестову транзакцію і перевірте, що `order-status.js` справді самостійно довершує бронювання, якщо вебхук штучно "не спрацював".
4. **`wash_boxes.is_active`** — якщо міграцію з попереднього кроку (`alter table wash_boxes add column is_active...`) ще не застосовано, код трактує всі бокси як активні (безпечний фолбек). Після додавання стовпця вимкнені в адмінці бокси одразу перестануть пропонуватись і на сайті.
5. **WayForPay-реквізити зараз глобальні (Vercel env vars), а не per-location** — у самій адмінці (`admin/services.html`) вже є окрема таблиця `location_payment_credentials` для реквізитів WayForPay кожної мийки. Сайт цей механізм поки не використовує. Якщо власник змінить реквізити через адмінку, на сайті доведеться оновлювати Vercel env vars вручну. Можна переробити `create-payment.js`, щоб він читав реквізити з `location_payment_credentials` замість env vars — скажіть, якщо це потрібно.
6. **`payment_links.created_at`** — м'яке утримання слоту (п.3 вище) припускає, що в таблиці `payment_links` є стандартна колонка `created_at`. Якщо назва інша, поправте фільтр у `api/_lib/availability.js`.

## Деплой

Vercel підхоплює `/api/*.js` як serverless-функції автоматично, окремого налаштування білду не потрібно. Framework Preset: **Other**, Build Command — порожній, Output Directory — `.`.
